# 枪械贴图图集设计（全局惰性图集 + 变体槽 + UV 换写）

状态：设计定稿，待实施
前置：`44af8f2`（发光面具 / 染色贴图资源查找缓存）已落地
日期：2026-09-24

---

## 1. 背景

满配枪 = 机匣 + 最多 ~10 个模块，每模块独立贴图。BEWLR 物品（GUI 图标、
掉落物、手持）每帧对每把枪走完整模块树渲染，而每个模块的
`RenderType.entityCutoutNoCull(自己的贴图)` 互不相同——`getBuffer` 每次换
类型都会把上一桶**立即冲刷成一次独立绘制**。

实测（探针，10 把满配枪可见，修复资源查找缓存**之后**的稳态）：

| 分项 | 每秒耗时 | 说明 |
|---|---|---|
| 模块 reRender（含批次冲刷） | ~290ms | **本次设计的目标** |
| 其余（NBT/骨骼快照/染色查询） | <20ms | 已由 44af8f2 解决 |

一把满配枪 ≈ 11 次立即绘制，单次 ~57μs（CPU + 驱动 + 贴图绑定）。
绘制次数是结构性成本：**模块数 × 贴图数决定了它，只有让多个模块共享
同一张贴图才能消除它。**

## 2. 目标

- 满配枪的绘制数从 ~11 降到 1–2（本体图集 1 次 + glow 图集 1 次）
- 全场枪共享图集 → 不同配置的枪之间也合桶（每帧 1–2 次绘制封顶）
- 显存有界：由画布尺寸常量决定，与枪数、配件数无关
- 保持 44af8f2 已恢复的帧率水平，并进一步逼近无枪基线

## 3. 非目标

- 不处理 >64×64 的模块贴图（走降级路径，见 §9）
- 不合并 glow pass 到本体 pass（发光是不同 RenderType，维持 2 draws）
- 不优化工作台/ghost 预览（低频路径，维持现行逐贴图渲染）
- 不做离线资产管线（拼包脚本等，违反创作者透明约束）

## 4. 约束（用户给定）

| 约束 | 内容 |
|---|---|
| 创作者透明 | gunpack 数据包工作流零变化：每模块一张贴图、`_glowmask`/`_dye` 掩码照旧，无映射表无构建步骤 |
| 尺寸异构 | 贴图 16–64px 常见；≤64px 入图集，>64px 强制降级 |
| 全 RGB 染色 | 任意十六进制配色，配色组合数无上界 |
| 规模 | 最终生态可能有**几百个配件** |
| 降级安全 | 任何图集容量问题都不得崩溃或渲染错误，只允许退回现行路径 |

## 5. 方案选型（否决记录）

| 备选 | 否决原因 |
|---|---|
| 离线拼包脚本 | 创作者不透明；加模块要重跑拼图 |
| per-gun 画布（每枪一张图集副本） | 槽位预算 = 画布面积，画布按枪复制 → 几百配件需要 512+ 画布 × 枪数上限，显存爆炸；相同配置才合桶 |
| 整图集副本 × 染色组合 | 全 RGB 下组合无上界，256KB/组合 爆显存 |
| **全局惰性图集 + 变体槽（本方案）** | 常量显存、槽位预算大、跨枪合桶，代价是可控的 UV 换写 |

## 6. 架构

### 6.1 全局图集与档位区域

运行期维护**一张**动态图集（`DynamicTexture`），画布尺寸是全局常量
（见 §10 预算表），预先划分为三个**档位区域**，区域内是等尺寸槽位：

```
1024×1024 画布（推荐默认）：
┌──────────────────────────┐
│  64区  128 槽（16×8）     │  y 0–511
├──────────────────────────┤
│  32区  256 槽（32×8）     │  y 512–767
├──────────────────────────┤
│  16区 1024 槽（64×16）    │  y 768–1023
└──────────────────────────┘
```

- 贴图按 `min(档位 ≥ max(w,h))` 入区：16→16 区、17–32→32 区、33–64→64 区
- **槽不必被填满**：UV 映射是仿射变换 `u' = (槽x + u·贴图w) / 画布宽`，
  非正方形或小于槽的贴图放槽原点即可
- 关闭 mipmap，区域边界由档位天然隔开（渗色风险见 §11）

### 6.2 槽位注册表（核心不变量）

`贴图键 → 槽位` 的全局 map，**首次被渲染到时分配**，会话内终身稳定。

> **不变量：贴图键 → 图集坐标，只依赖（键自身 + 会话分配历史），
> 绝不依赖任何一把枪的配置集。**

这是整个方案成立的根基：GeckoLib 模型是共享对象、UV 只能有一套当前值，
坐标必须对"这把枪装了什么"完全无感，模型的一次性 UV 改写才有意义。
（朴素装箱的位置依赖集合内容，直接违反此不变量，故不可用。）

贴图键两种：

- **基础键** = 贴图 id（模块/机匣的本体贴图）→ 基础槽，**永生**
- **变体键** =（贴图 id + 染色三元组的稳定哈希）→ 变体槽，**LRU 淘汰**
  （全 RGB 染色的组合无上界，变体是唯一需要封顶的轴；基础槽是有限集
  ——配件本体贴图数——不需要淘汰）

### 6.3 UV 换写

每个（被图集覆盖的）烘焙模型维护：

- `原始 UV` 快照：首次改写前逐 quad 备份（几百个 float/模型）
- `当前槽` 标记

绘制前流程：查注册表得本帧应指向的槽 → 与 `当前槽` 不同则把原始 UV
仿射重写到新槽 → `reRender`（顶点发射时从 quad 读 UV）。

正确性依据：

- 渲染单线程（render thread 串行），无数据竞态
- GeckoLib 的 `isReRender` 只跳过动画重放，**顶点写入总是执行**，
  换写后立即生效
- **每次绘制都查注册表、不缓存槽指针**：变体槽被 LRU 淘汰后模型不持有
  过期引用，下次绘制自然重新分配并换写

成本：稳态（全场同配置/未染色）**零换写**；最坏（同模块多配色同屏）
每帧每模块 2 次，每次几百个 float 的算术，微秒级。

### 6.4 glow 图集

第二张同布局图集，像素 = 基色 × glowmask alpha 预乘（沿用 GeckoLib
AutoGlowingTexture 的配方），槽位注册表共用（同一贴图键同一槽）。
RenderType 为 eyes/fullbright，与本体 pass 分开 → 全枪稳定 2 draws。

顺带修复一个既有 quirk：现状染色模块 glow 失效（glow 掩码查找用的是
resolve 后的染色贴图 id，永远落空）。图集路径里 glow 槽直接烘
"染色后基色 × 掩码"，染色模块的发光恢复。

### 6.5 烘焙管线

1. 解码后的 PNG 按贴图 id 全局缓存（NativeImage，一次解码终身复用）
2. 染色像素数学复用 `DyedTextures.dye()`（灰度 × 颜色，保 alpha）
3. blit 入槽（基础贴图直接拷，变体先逐像素染色）
4. 上传：新槽出现时整图上传一次（1024² ≈ 数 ms，仅发生在发现新内容时；
   若成为瓶颈，后续换 `glTexSubImage2D` 局部上传，见 §11）

### 6.6 渲染路径集成点

| 位置 | 改动 |
|---|---|
| `GunModulesLayer.mount` | 贴图可入图集时，RenderType 用 `entityCutoutNoCull(图集id)`；绘制前走 §6.3 换写；否则现行路径 |
| `GunGeoModel.getTextureResource` | 机匣贴图同样走图集（机匣也要合桶，否则全枪 2 draws 起步） |
| ghost 预览 | `entityTranslucent(图集id)`，同贴图不同类型，照样合桶 |
| 工作台/掉落物 rest pose | 与手持共用图集路径，无特殊分支 |

## 7. 生命周期与失效

- **F3+T / 枪包热重载**：清空注册表 + 释放两张图集 + 代数计数器 +1；
  模型侧发现代数变化即丢弃 UV 快照与当前槽标记，重新走首次改写。
  挂在现有客户端 reload listener（44af8f2 引入）同一链路
- **变体槽 LRU**：默认上限 256（常量）。访问即摸表（`LinkedHashMap`
  accessOrder 语义）；淘汰仅释放槽位，不做任何回调

## 8. 降级梯子（任何一级都不崩溃、不渲染错误）

| 情形 | 行为 |
|---|---|
| 贴图 >64×64 | 该贴图走现行逐贴图路径（1 draw/模块，即今天的成本） |
| 档位区域满 | 尝试更大档位区域；仍无槽 → 同上 |
| 整图集满 | 同上 |
| 已降级的贴图键 | 注册表记 `NO_SLOT`，避免每次绘制重试探测 |

一把"1 个超尺寸瞄具 + 9 个常规模块"的枪 ≈ 2 draws（9 合桶 + 1 降级）。

## 9. 显存与性能预算

| 画布 | 本体图集 | +glow | 槽位容量 | 结论 |
|---|---|---|---|---|
| 512² | 1MB | 2MB | ~350 | 单枪包生态够用 |
| **1024²（默认）** | **4MB** | **8MB** | **~1400** | **覆盖几百配件** |
| 2048² | 16MB | 32MB | ~5600 | 预留，一般不必 |

- 显存与**枪数无关**（没有 per-gun 条目——那是被否决的方案）
- 预期绘制数：满配枪 11 → 2；全场任意数量枪 → 每帧 2–4 次
  （本体/glow × 被 HUD 或世界 pass 打断的次数）

## 10. 配置

- `Config.atlasGuns`（客户端，默认开）：一键回退全部图集逻辑到现行路径，
  出问题时用户可自证
- 画布尺寸、变体槽上限、LRU 容量为代码常量（调整成本一行）

## 11. 风险与开放问题

| # | 风险 | 缓解 |
|---|---|---|
| 1 | **GeckoLib 烘焙 UV 的归一化基准**：geo json 的 `texture_width/height` 若与 PNG 实际尺寸不一致（留白写法），UV 换写的 `贴图w` 必须取 PNG 实际尺寸而非 json 声明。实施 M1 时先核实 `BakedGeoModel` 是否携带 texWidth/Height；不可靠则一律从注册表查 PNG 实际尺寸 | 实施首日验证 |
| 2 | 渗色：关 mipmap 后主要是线性过滤的邻槽渗入 | 槽内 1px 边距（写入时贴图向内缩 0.5px 或复制边缘行）；档位区域边界天然隔离 |
| 3 | 新槽频繁出现的整图上传 hitch（如逛武器库展示厅） | 短期容忍（毫秒级、仅首见）；优化项：局部上传 |
| 4 | 半透明贴图与 cutout 渲染语义 | 图集不改变 RenderType 语义，行为与现状一致；仅渗透边界需 §2 验证 |
| 5 | 染色视觉回归 | 变体槽像素数学与 `DyedTextures` 同源，验收时逐模块对比 |

## 12. 实施里程碑

- **M1 槽位注册表 + 图集烘焙 + UV 换写**：未染色模块走图集（风险 #1
  在此验证），compileJava + runClient 视觉验证
- **M2 机匣接入 + glow 图集**：全枪 2 draws；染色模块 glow 恢复验证
- **M3 变体槽 + LRU + 染色接入**：全 RGB 配色回归
- **M4 降级加固（NO_SLOT 记忆、>64 路径）+ 重载失效 + Config 开关**
- 每步独立可编译、可运行、可回退；完成一段提交一段

4. F3+T 后外观与槽位正确重建
